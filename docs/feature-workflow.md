# 기능 개발 절차

## 기능 개발 순서

1. 메인 세션이 `docs/feature-template.md`를 바탕으로 `docs/features/<slug>.md` 초안을 쓰고 사용자 확인을 받는다. 열린 질문이 남아 있으면 구현을 시작하지 않는다.
2. test-writer가 이 기능의 테스트를 모두 작성하고 한 번 실행해 백엔드·프론트 모두 red인지 확인한다. 컴파일 실패도 red다.
3. backend-dev, frontend-dev가 프로덕션 코드를 작성한다. 컴파일만 확인하고 테스트는 실행하지 않는다.
4. 사용자가 `./gradlew check`와 `./gradlew integrationTest`로 green을 확인한다. 메인 세션은 Gradle을 대신 실행하지 않는다.
5. 테스트로 확인할 수 없는 레이아웃, 스크롤, 한글 입력이 바뀌었으면 사용자가 화면을 본다. 새 API가 있으면 메인 세션이 `scripts/api-smoke.sh`에 호출을 추가해 실제 jar로 확인한다.
6. 사용자가 `/code-review`를 직접 실행하고 재작업 여부를 정한다. 메인 세션은 리뷰를 자동으로 실행하지 않는다.
7. `develop`으로 PR (제목은 Conventional Commits 형식) → squash merge

## 막혔을 때

- 에이전트는 원인과 시도한 것을 보고하고 멈춘다. 메인 세션은 기능 문서의 `제약 사항`에 적고 사용자에게 알린다. 사용자가 재작업, 요구 변경, Issue로 미루기 중에서 정한다.
- 같은 문제로 두 번 실패하면 세 번째를 돌리지 않고 멈춰서 알린다.
- 내용의 수명에 따라 옮겨 둔다.
  - 이 기능을 하는 동안만 필요한 것: 기능 문서의 `제약 사항`
  - 그 기능의 결정과 알려진 한계: PR 본문
  - 앞으로 모든 기능에 적용되는 것: `.claude/rules/`
  - 지금 못 고치고 나중에 처리할 것: GitHub Issue

## 기능 문서

- `docs/features/<slug>.md`는 git으로 추적하지 않는 로컬 작업 문서다. PR을 만들 때 요구사항과 결정 요약을 PR 본문에 옮겨 squash 커밋에 남긴다.
- 문서는 메인 세션만 고친다. 진행 기록의 메모에는 주요 내용만 적는다.
- 에이전트에게는 문서의 정확한 경로를 넘긴다. 요구사항을 프롬프트에 다시 옮겨 적지 않는다. git이 무시하는 파일은 검색 결과에서 빠질 수 있으므로, 검색하지 않고 그 경로를 바로 읽는다.
- 결정이 바뀌면 코드보다 문서를 먼저 고친다.
- 머지한 뒤에는 문서를 갱신하지 않는다. 그 뒤로 현재 동작의 기준은 코드와 REST Docs다.
- 여러 기능에 적용되는 결정은 `.claude/rules/`로 옮긴다.
